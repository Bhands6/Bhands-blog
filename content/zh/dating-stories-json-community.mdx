想做个小站，让网友匿名讲讲自己的相亲经历——甜蜜的、搞笑的、感动的、吐槽的。

这类站有个很现实的前提：**它可能只有几十个用户，也可能某天被转到某个群里突然来几千人**。为这个量级去养一台数据库、配一套备份、维护一份 migration，成本明显不划算。所以我给自己定了个约束：

> 不装 MySQL，不装 SQLite，数据就是几个 JSON 文件。

这个约束听起来是在省事，实际上是把复杂度从「数据库配置」搬到了「自己保证数据不出错」。后来复盘，**真正吃掉大部分时间的正是搬过来的那部分**。

## 二、一个 JSON 文件当数据库，最难的三件事

零数据库的意思很直白：`data/stories.json` 里存着全部故事、评论、点赞和删除凭证，`data/feedback.json` 存反馈，`data/views_log.json` 存浏览量防刷记录。**备份 = 复制 `data/` 目录**，迁移 = 把目录拷贝到新机器。这部分确实很省事。

代价是：数据库替你做的事，现在都得自己做。

### 1. 写盘必须是原子的

最直觉的写法是打开文件、清空、写入：

```php
$fp = fopen($f, 'w');   // ← 文件此刻已被清空
fwrite($fp, $json);     // ← 还没写完
fclose($fp);
```

这中间存在一个窗口：**文件已经被清空，但新内容还没落盘**。如果这时进程被杀、容器重启、或者机器断电，你得到的是一个残缺的 JSON。而数据文件是唯一数据源，坏一次全站都读不出来。

改法是先写同目录的临时文件，再 `rename` 覆盖：

```php
function atomic_write(string $file, string $content): bool
{
    $tmp = $file . '.tmp';
    if (@file_put_contents($tmp, $content, LOCK_EX) === false) { return false; }
    if (!@rename($tmp, $file)) { @unlink($tmp); return false; }
    return true;
}
```

`rename` 在同一文件系统内是原子操作——读者要么看到完整旧内容，要么看到完整新内容，不存在中间态。

### 2. 锁不能锁在数据文件上

有了原子写，接着要解决并发。互斥用 `flock` 很自然，但**锁哪个文件**有个坑：

```php
$fp = fopen($file . '.lock', 'c');   // ← 注意是 .lock，不是数据文件本身
flock($fp, LOCK_EX);
```

如果直接把锁加在数据文件上，会这样失效：请求 A 拿到锁 → 写完临时文件 → `rename` 覆盖数据文件。**此时数据文件的 inode 已经被换掉了**，而 `flock` 锁的是 inode。请求 B 过来打开数据文件，锁到的是全新的 inode，于是 A 和 B 同时认为自己持有排他锁——互斥直接归零。

所以锁必须落在一个**永远不会被替换的文件**上。`data/*.lock` 这些 0 字节的小文件就是干这个的，删掉也会自动重建。

### 3. 「读—改—写」必须全程持锁

前两步只保证了「写」这一下是安全的，但真实场景是读出来、改、再写回去。如果只锁最后那次写：

```
请求 A: 读（likes=10） ......... 改（11） 写
请求 B:      读（likes=10） ......... 改（11） 写
                              ↑ B 整份覆盖 A 的结果
```

两边都读到 10，都算出 11，后写的把先写的覆盖了。修复前的实测数据是：**4 个 worker 并发打 20 个点赞，最终 `likes` 只到 10，而且有 5 个请求直接失败**。

所以要把读写包进一个全程持锁的事务里：

```php
function db_transaction(callable $fn)
{
    $lock = lock_guard(DATA_FILE);          // 加锁
    if (!$lock) { fail('数据文件繁忙，请稍后重试', 503); }

    $db = json_decode(...);                 // 读
    $before = json_encode($db);
    $result = $fn($db);                     // 改（回调在持锁状态下执行）
    $after  = json_encode($db);

    if ($after !== $before) {               // 只有真的变了才写盘
        atomic_write(DATA_FILE, json_encode($db, ...));
    }
    unlock_guard($lock);                    // 解锁
    return $result;
}
```

同一组实测，改完后**精确得到 20**。

顺带说明：Node 侧的 `server.js` 不需要这个事务——单线程 + 全同步文件 IO，一次请求处理中途不会被别的请求打断，天然不存在这个竞态。所以同一个问题，两个后端里只需要在 PHP 那边解决。

### 另外两个更容易忽略的坑

**限流记录的清理窗口**。清理过期记录时，如果拿「当前请求动作」的窗口去过滤所有动作的记录就会出事——发布是 600 秒窗口，评论是 300 秒，反馈是 1800 秒。用 300 秒去清，发满 5 篇之后随便评论一条，**发布额度就被重置了**。现在按各自动作自己的窗口判过期。

**客户端 IP 别乱信**。`X-Forwarded-For` 是个请求头，谁都能写。站前面没有反向代理的时候信任它，等于把限流和浏览量去重拱手让人：加一个请求头就能无限刷。所以默认值是这样的，将来挂了 nginx/CDN 再打开：

```php
const TRUST_FORWARDED_FOR = false;
```

## 三、匿名站点的难点在「防」

允许任何人匿名发表内容，意味着**每一个输入都是敌意输入**。这一块是整个项目改动最密集的地方，也是踩坑最多的。

### `/data/` 目录曾经是全网可下载的

这是最严重的一个。Apache 会把 `data/` 当普通静态目录直接返回，于是：

- `站点/data/admin_key.txt` → 拿到管理密码
- `站点/data/stories.json` → 拿到全站数据，**以及每篇故事的删除凭证 `editKey`**

第二条的后果不只是数据泄露——`editKey` 是"发布者身份"的凭证，拿到它就能删掉任何人的故事。

修法是三层拦：镜像里的 Apache `deny-data.conf`、仓库自带的 `data/.htaccess`、Node 开发服务器同步封堵。**nginx 站点 `.htaccess` 完全无效**，必须自己加：

```nginx
location ^~ /data/ { deny all; return 404; }
```

部署文档里给了验证方法：浏览器访问 `域名/data/admin_key.txt` 必须返回 403 或 404。能下载到内容，就说明密码已经公网泄露了。

### 别在公开仓库里留兜底密码

一开始管理密码是个写死的默认值，方便自己用——但它同时存在于公开仓库里，等于**所有忘记改密码的部署都没有密码**。现在改成首次访问时自动生成 12 位随机密码落盘，代码里没有任何默认值。忘记配置不会导致"没有密码"，但也不会有一个所有人都知道的密码。

登录本身也加了限流：同一 IP 连错 5 次锁 15 分钟。

### 凭证比较要用定长比较

故事的删除凭证 `editKey`、评论的删除凭证 `delKey` 都是随机串，校验时如果直接用 `===`，比较耗时会随「相同前缀长度」变化，理论上能被逐字节试出来。改用：

```php
if (!hash_equals((string)$s['editKey'], $editKey)) { ... }
```

还有一个更隐蔽的点：**`delKey` 不能出现在任何 GET 输出里**。发表评论成功时它会随响应下发一次，之后所有列表接口都必须把它剥掉——否则任何访客翻一遍接口就能拿到别人的删除凭证。做法是在输出函数里走**显式字段白名单**，而不是"过滤掉敏感字段"。

### 浏览量去重的粒度

第一版的键是「IP + 故事 id」，24 小时窗口。上线后发现一个问题：**同一个 WiFi、同一间公司、同一个小区出口 IP 下的所有人被当成同一个人**，一个人看过之后，其他人 24 小时内都不计数。

改成「浏览器 visitorId + 故事 id」——前端生成随机 id 存 localStorage，请求时带上。这样同一 IP 下不同浏览器各记一次。同时保留「IP + 故事 id」的窗口内计数上限（20 次）兜底，防止有人清 localStorage 刷量；不带 `vid` 时退化成纯 IP 去重。

### 存储型 XSS

管理页会展示访客提交的昵称、反馈内容、故事标题。有一版这些字段是直接拼进 HTML 的——也就是说，**访客提交一个带 `<script>` 的昵称，站长打开管理页就中招**。修法是补一个转义函数，把所有访客可控字段全部过一遍。

发布的故事正文也做了净化，但方向不太一样：正文允许 HTML（这是功能），所以只摘掉危险部分，保留结构和样式：

```php
$html = preg_replace('#<\s*script\b[^>]*>[\s\S]*?<\s*/\s*script\s*>#is', '', $html);
$html = preg_replace('#\son\w+\s*=\s*("[^"]*"|\'[^\']*\'|[^\s>]+)#i', '', $html);   // onclick= 之类
$html = preg_replace('#(href|src)\s*=\s*("|\')\s*(javascript|vbscript):[^"\']*#i', '$1=$2#', $html);
$html = preg_replace('#expression\s*\(#i', '', $html);
```

### 让陌生人写的 HTML 待在沙箱里

净化只能拦已知的危险写法，而"用户上传自己排版的 HTML 故事、样式 100% 原样显示"是这个站的核心功能，光靠正则不可能做干净。

所以换了个思路：**不净化渲染，而是把渲染关进沙箱**。用户排版的 HTML 通过独立接口以 `CSP: sandbox allow-scripts` 输出，前端用 iframe 嵌进去——文档被当成独立源，里面的脚本碰不到站点的 localStorage、cookie 和接口。

`allow-scripts` 是必须开的，因为很多排版用了滚动显现动画；但没开 `allow-same-origin`，所以它拿不到任何站点数据。

这里还有个细节：用户上传的 HTML 里，控制入场动画的 class 名五花八门（`visible` / `active` / `show` / `fade-in` / `entered`……），不可能要求每个人统一。所以在输出时**站点自己附带一段驱动脚本**，把常见的那批 class 名在滚动到位时统一加上去，动画就都能跑起来，而用户的原始代码一个字都不用改。

### 路径穿越的一个细节

Node 侧的静态服务要防止 `../../etc/passwd` 这类路径逃逸。常见写法是：

```js
if (!filePath.startsWith(ROOT)) return 403;
```

但这会把**同前缀的兄弟目录**误判成站内——如果站点目录叫 `缘份故事屋`，那 `缘份故事屋-evil` 也能通过检查。正确的做法是拿 `ROOT + 分隔符` 去比。

## 四、一份数据，两个后端

架构上有两个后端，服务同一份 `data/`：

```
浏览器 ──► 纯静态前端（index / publish / admin / ...）
              │
              ▼  fetch api.php?route=xxx
      ┌───────────────┐
      │  api.php      │  PHP 单文件后端（生产）
      │  或 server.js │  Node 零依赖开发服务器（接口完全对齐）
      └───────┬───────┘
              ▼  JSON 文件读写（独立 .lock 互斥 + 临时文件原子替换）
      data/stories.json / feedback.json / views_log.json ...
```

- **`api.php`**：1667 行，19 个接口，部署到 PHP 主机（宝塔）用，不需要任何 PHP 扩展
- **`server.js`**：1408 行，同样这 19 个接口，`node server.js` 就能起，零依赖、不用 `npm install`

写两套后端听起来是重复劳动，但收益很实在：**本地开发和线上调试的代码路径完全一致**，前端不需要区分环境。代价是任何接口改动都得两边同步——所以限流阈值这类配置在两份代码里各写一份，改动时必须两边一起改。

## 五、发布页：不会写 HTML，就交给 AI

发布有两种模式：纯文本，或者 HTML 排版。

![发布页：左侧是表单（昵称、标题、单选框标签、正文），右侧是「分享你的故事」说明与 HTML 文件上传入口](/blog/dating-stories/publish.jpg)

HTML 模式能做出很精致的排版，但**它默认的受众是不会写 HTML 的人**。所以切到 HTML 模式时会弹一个引导：

![AI 排版引导弹窗：三步指引 —— 用几句话写下剧情、让 AI 生成完整 HTML、复制保存为 .html 文件后上传；下方是可一键复制的提示词模板，以及 DeepSeek / 豆包 / 小米 MiMo 的直达入口](/blog/dating-stories/publish-ai.jpg)

三步是：把故事写出几句话 → 丢给 AI 让它生成一个完整 HTML → 复制保存成 `.html` 上传。提示词模板可以直接一键复制，省得用户自己琢磨怎么描述要求。

这个功能解决的是**能力门槛**问题，而不是技术问题——如果只支持纯文本，那些想认真排版的人就写不出来；如果只支持 HTML，大部分人根本用不了。

另一个细节是**删除凭证**：发布成功后，浏览器会拿到一个一次性的 `editKey` 存在本机，之后凭它删除自己的故事。**换浏览器或清缓存，凭证就没了**——这是零用户系统的必然结果，也是个需要讲清楚的取舍：换设备迁不走"所有权"。

## 六、站长管理台

管理页是密码保护的单页：

![管理台登录界面：只有站长能打开，输入管理密码解锁「网友反馈箱」](/blog/dating-stories/admin.jpg)

解锁后有反馈箱和故事管理两块，都在同一页：**反馈箱**（查看、标记已读、删除，含网友留的联系方式）、**故事管理**（最新排序、标签筛选、搜索、点击预览、编辑、置顶、批量删除）。顶部常驻 6 个指标：故事数、点赞、浏览、评论、今日新增、未读反馈。

有一处交互改得挺值：删除和导出原先是浏览器原生 `confirm()`，而 `confirm()` 只有「确定 / 取消」两个按钮。导出功能有两个选项（导出故事数据 / 导出反馈数据），硬塞进 `confirm()` 之后变成了「点确定导出故事、点取消导出反馈」——**用户以为"取消"是关闭弹窗，结果反而下载了一份 JSON**。后来换成自定义弹窗，两个选项卡片点哪个导哪个，关闭和点遮罩都只关窗。

## 七、跑起来

本地开发零依赖，不需要 `npm install`：

```bash
git clone https://github.com/Bhands6/dating-stories.git
cd dating-stories
node server.js          # http://localhost:8000（端口被占自动 +1）
```

服务器部署三种方式，最省事的是宝塔：建站（PHP 7.4+，**不勾选数据库**）→ 把文件放进站点根目录 → `data/` 给写权限 → 确认 `data/` 无法通过 HTTP 访问。全程不需要任何 PHP 扩展。

或者用 Docker：

```bash
docker compose up -d --build
# http://服务器IP:8010（端口在 docker-compose.yml 里改）
```

镜像里做了三件事省心：生产级 `php.ini`（`display_errors=Off`，否则运行时 Warning 会混进 JSON 响应，前端直接报 `Unexpected token '<'`）、启动时自动把挂载的 `data/` 属主修正为 `www-data`、`data/` 为空时自动用 `seed.json` 初始化。

## 八、复盘

零数据库这个决定，回头看是对的，但**它并不省事，只是把复杂度换了地方**：

| 数据库替你做的 | 换成自己做的 |
|---|---|
| 事务 / 行锁 | 独立 `.lock` + 全程持锁 + 原子写 |
| 备份恢复 | 复制 `data/` 目录 |
| 并发写一致性 | `db_transaction()`（PHP 侧） |
| 索引与查询 | 全部读进内存再筛（数据量小的时候完全够） |

真正受益的是**运维成本**：没有连接池要调、没有版本要升、没有连接数上限、搬机器就是拷贝一个目录。代价是数据量一旦上去就会很难受——现在每写一次都要把整个 JSON 序列化一遍，这个模式的天花板很低。

但这个站的天花板本来就低。**在几十到几千用户这个区间里，"没有数据库"不是妥协，是个合理选择。**

安全那部分则是另一种体会：一个允许匿名发言的站点，作者（我）必须同时扮演攻击者。上述每一条——目录暴露、兜底密码、请求头伪造、XSS、凭证比较、沙箱——都不是理论上的隐患，是上线后逐个发现、逐个补上的。

最后说一句许可证：这个仓库的 README 徽章写的是「用途 · 个人项目」，**没有采用标准开源许可证**。仓库公开可见，但如果你想拿它的代码做别的用途，请先确认授权。
